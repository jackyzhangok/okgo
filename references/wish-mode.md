# 许愿模式（Wish Mode）

> 目标：用户给**一句需求**，agent 自己推进到「本地可运行 + 已验证 + 有交付报告」。
> 前提：三条铁律（验收标准、先红后绿、独立复核）**不变**。变的只是「谁拍板」。
> 适用：MVP、内部工具、已有仓库的新功能、原型。
> 不适用：合规/支付/多租户权限、生产部署、品牌级视觉、需要人类审批的对外动作。

---

## 0. 一句话契约

输入一句需求 → 输出：

- 可运行的主流程（从真实入口）；
- 本次运行的测试与门禁证据；
- 有 UI 时的截图；
- 假设账本 + 未验证清单；
- 交付报告（改了什么 / 为什么 / 怎么验证 / diff 规模 / 下一步）。

**不承诺**：上线级质量、生产部署、未经你确认的业务正确性。

---

## 1. 启动

触发语：「许愿模式」「一路做完」「不用问我，做完给我看」「wish mode」。

未触发 → 按 `guided` 模式走三闸门，不要自作主张升格。

触发后立即做，**不等确认**：

1. 读仓库：包管理器、框架、现有门禁、目录约定、既有 `AGENTS.md`；
2. 建工作区：已有仓库建分支；新项目 `git init` + 首个提交（不推送）；
3. 落规则与流程文档（缺 `AGENTS.md` 就按启动动作自动生成）；
4. 写假设账本（模板：`assets/assumption-ledger.md`）。

---

## 2. 最多问 3 个问题

只问「不问就会整体做错方向」的，一次问完，并**给出你的默认答案**；用户不答就按默认继续。

可问的三类：

1. 目标用户与核心动词（做给谁、完成哪一件事）；
2. 硬约束（必须复用/必须避开的系统、期限、合规）；
3. 交付边界（要不要登录/多用户/持久化/离线）。

其余一律写成假设，**不问**。已回答过的信息不重复问。

---

## 3. 假设账本（先写后做）

每条假设四要素：**假设 / 依据 / 影响面 / 错了的代价与回滚方式**。

- 只写影响行为的假设，不写常识；
- 禁止无依据假设（依据 = 需求原话、仓库事实、行业惯例）；
- 每阶段结束更新：已确认的移出并记入决策，新出现的补上；
- 交付报告必须附账本；**隐藏假设视为缺陷**。

---

## 4. 默认决策表

除「例外」列外，一律按默认执行，不等人点头。

| 决策 | 默认 | 例外（才停） |
|---|---|---|
| 工作区 | 已有仓库建分支；新项目 `git init` + 本地提交 | 用户明确要求不建 git |
| 执行方式 | 单人顺序执行 | task ≥8 且互不共享文件 → 并行 |
| 新增依赖 | 默认不加；必须加时选最小、维护良好、许可兼容，记入账本 | 付费、私有源、系统级安装 |
| 预算 | 每 task ≤8 文件 / 净增 ≤400 行；超出拆批 | 单 task 超 3 倍 |
| 门禁 | 不放宽、不改阈值；存量红项登记为基线 | 不改门禁就无法通过 |
| 视觉 | 给 2 个方向，按信息密度与行业惯例选 1，记入账本 | 品牌级 / 对外营销页 |
| 数据 | 本地可替代（SQLite / 内存 / 样例数据） | 必须连生产库或付费 API |
| 提交 | 一 task 一提交，仅本地 | 推送 / PR / 合并 / 发布 |
| 部署 | 不做 | 用户要求部署 |
| 文档 | 与代码同轮更新 | — |

---

## 5. 闸门改为自检

用户不再逐闸门确认，但你仍要过同样的检查，并留下记录。

**闸门 1（契约自检）**：每条验收项能否用一条命令或一个观察验证？不能就改写；实在写不出，用「假设 + 最小可验证行为」替代，并记入账本。

**闸门 2（设计自检）**：数据 / 接口 / 权限 / 失败 / 安全 五项是否都有答案？有 UI 时是否有视觉方向 + 状态清单（空/加载/错误/禁用/成功）？

记录格式：

```text
自检: 通过 — <证据或理由>
自检: 不通过 — <缺什么> → <怎么改>
```

自检不通过 → 自己改；改不动 → 停（见第 7 节）。交付时每个验收项必须能指回证据。

---

## 6. 独立复核自动化

- **复核者**：新会话 / 子代理 / 另一工具；实现者自评不算。
- **输入**：任务契约 + 仓库 + diff（base..head），**不给实现者自评**。
- **最多自动修 2 轮**；第 3 轮仍不通过 → 停，交缺陷单。
- 复核者不改代码；改了就要换人。

---

## 7. 硬停条件（唯一允许打断用户的情况）

1. 不可逆 / 破坏性：删数据、改生产、force push；
2. 安全敏感：密钥、认证、支付、权限模型；
3. 外部副作用：推送、开 PR、部署、发布、对外发消息；
4. 需要付费、私有源或系统级安装；
5. 预算超限：单 task 超 3 倍；
6. 需求自相矛盾且无合理默认；
7. 环境不可用：无网络、依赖装不上、端口冲突无解；
8. 复核连续 2 轮不通过；
9. 用户打断。

停下时必须给：**卡点 / 已尝试 / 可选方案（含默认推荐）/ 继续所需的最小输入**。给不出这四项，说明你还没准备好停。

---

## 8. 完成定义

必须同时满足：

- 主流程从真实入口跑通；
- 本次运行的 `type-check` / `test` / `check` / `build` 证据（命令 + 退出码 + 关键输出）；
- 有 UI 时截图覆盖默认 / 空 / 错误 / 加载；
- 无 TODO / 调试输出 / 占位实现；
- 假设账本 + 未验证路径；
- 交付报告完整。

没做到就写「未完成 + 原因」，不写「应该没问题」。

---

## 9. 失败与返工

- 错误假设 → 记「假设失效」→ 评估影响面 → 能局部回滚就回滚，不能就重做该切片；
- 连续两次同类失败 → 停，报告根因假设，不硬试；
- 返工不得为了让测试变绿而放宽断言或门禁。

---

## 10. 切回 guided

用户说「停」「一步一步来」「先确认」→ 立即停止自动推进，回到三闸门；已完成部分作为 guided 的输入，不推倒重来。

---

## 11. 反模式

| 反模式 | 现实 |
|---|---|
| 把「许愿」理解成「不问就乱做」 | 不问的是可推断项，核心方向仍要确认或明确假设 |
| 假设只在脑子里 | 不记录 = 埋雷，交付时无法追溯 |
| 自检写成「已检查」 | 没有证据的自检无效 |
| 自己复核自己 | L2 不允许，必须换上下文 |
| 用「未验证」当交付 | 未验证必须列出并说明原因与建议验法 |
| 为了跑完而砍验收项 | 砍掉的验收项会以缺陷形式回来 |
