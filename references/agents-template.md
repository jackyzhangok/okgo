# AGENTS.md — {{PROJECT_NAME}} 项目规则

> **权威性**：本文件是本项目唯一权威规则（canonical）。`CLAUDE.md` 如存在，只是指向本文的指针，规则正文只在本文维护。
> **性质**：只承载「怎么干活的规则」，不承载业务内容（业务见 `readme.md` / `prd.md` / `docs/design/`）。
> **优先级**：用户直接指令 > 本文 > 技能默认值。任何外部手册与本文件冲突，以本文件为准。
> **写法约束**：能自动拦的写成门禁；拦不住的写成「证据要求」。**一条规则如果没有对应的门禁或证据要求，默认它不会被遵守。**
>
> **核心公式：完整性 = 可枚举的验收清单 × 自动化检查 × 独立复核。**

## 0. 不可协商（冲突时这些优先）

1. **永不编造**：API、路径、函数名、参数、返回结构、依赖包名、测试结果——不知道就读源码、跑命令、查 `package.json`；仍不确定就说「我不确定，让我查」。
   - 调用任何 API 前先读定义，确认参数、返回、可空性与错误形态。
   - 新增 import 前「三查」：本包 `package.json` 已声明 → 锁文件有条目 → 依赖检查通过。
   - 禁止编造命令、脚本名、环境变量、文件路径、测试输出、截图。
2. **外科手术式变更**：每行改动可追溯到需求；不重构需求外代码、不加「以后可能用到」的抽象、不引入新依赖/新模式/新库。
   - **新增依赖/工具必须先问**，并说明现有依赖为什么不够。
   - **规模预算**：单次变更 ≤8 文件、净增 ≤400 行；超出**动手前**确认并拆分。
   - 豁免：纯新增门禁脚本/基线登记；仅为降低 size/complexity/duplication 的机械重构（须行为不变、测试不改、单独提交）。
3. **复用优先**：新增函数/类/组件/Hook/工具前，先搜索同名、同义、同职责实现；优先扩展或组合。相同逻辑出现第 3 次必须提取。能删就不新增；新公共抽象必须有 ≥2 个真实调用点。
4. **完成必须有证据**：交付前真跑门禁与测试，贴**本次运行**的命令、退出码、关键输出。「看起来对」「之前跑过」「应该没问题」都不算完成。没跑到的路径标注「未验证」。
5. **测试不可投机**：不得为让测试通过而修改/放宽/删除断言，不得特判测试输入。**凡改动测试文件，必须在交付说明单独列出并说明理由。** 测试全绿只证明测试全绿，不证明功能正确。
6. **不确定必须上报**：交付说明列出「最不确定的 3 处」和「未验证的路径」。禁止用「应该没问题」收尾。

## 1. 交互与任务分级

- 一律中文交互。
- 需求沟通「目标先行 + 迭代补充」；关键方向未定一次问清再动手。
- 需求有两种合理解释且影响输出时，先问，不默默选。
- 结论须有依据（输入、信源、可复现计算）。
- **非平凡需求先对齐验收标准，再动手**；写不出可判定验收标准的需求，不进入实现。

| 级别 | 判定 | 最低流程 | 复核 |
|---|---|---|---|
| L0 | 纯文档/注释/文案，无行为变化 | 相关门禁 + 说明 | 可免 |
| L1 | 单模块行为变更、修 bug | 契约 + 测试 + `check` | 用户抽查 |
| L2 | 新项目、新功能、跨模块、架构/数据/安全 | 契约 + 规格 + 骨架 + 分片 + E2E + 全量门禁 | **独立复核强制** |

新项目默认 L2。分级只升不降。

## 3. 目录与依赖契约

```text
{{PROJECT_NAME}}/
├─ apps/          # 可独立部署的应用
├─ libs/          # 被复用的库
├─ tools/         # 产物在仓库外的脚手架
├─ docs/          # 文档
├─ changes/       # 规格工件
├─ scripts/       # 门禁与工具脚本
└─ artifacts/     # 截图等验收产物（不入库或按需）
```

规则：

1. 新包只能落在 `apps/` / `libs/` / `tools/` 三根下。
2. **新增/移动/删除包必须同时更新** `docs/architecture/layout.md` 与分层登记脚本，否则 `check:layout` 失败。
3. **依赖方向**：后端不得引用前端；共享库不得引用业务包。由 `check:dep-direction` 强制。
4. **默认不发布 npm**：所有包 `private: true`；不得加 `publishConfig` 或发布令牌。确需发布单独决策并登记。
5. 库包源码直出，不产 `dist`（脚手架 bin 例外）。
6. 禁止兼容壳堆积：旧入口只减不增，删除时同步改调用方。

## 5. 开发流程（六阶段，不跳步）

```text
契约 → 验收清单 → walking skeleton → 分片实现 → 自动闸门 → 独立复核
```

| 阶段 | 必须做 | 闸门 |
|---|---|---|
| 1 契约 | 任务契约 + 验收项（功能/边界/集成/卫生） | 用户确认 |
| 2 设计 | 数据/接口/权限/失败/安全；有 UI 时定设计系统 | 用户 review |
| 3 计划 | 文件结构 + TDD 步骤级 task；tasks 最后写 | 计划可执行 |
| 4 实现 | 先骨架后功能；每片先测试后实现；每片全量回归 | 测试先红后绿 |
| 5 验证 | check + build + serve + E2E + 截图 + 卫生 | 全绿且有证据 |
| 6 复核 | 独立上下文逐条验证 | 复核通过 |

**立即停手的信号**：开始改契约外文件；想造第二套实现；验收标准写不出命令却继续写码；想让测试变绿而改断言；想临时装包或用 `any`/`@ts-ignore` 压错误；只跑相关测试就宣布完成。

## 6. 规格工件（L2）

顺序固定：`proposal.md`（为什么/改什么）→ `specs/` 或 `design.md`（行为与技术方案）→ `tasks.md`（最后写）。

- requirement 用 `The system SHALL ...` 句式；
- 每条 requirement 至少一个 `#### Scenario:`，用 `- **WHEN**` / `- **THEN**`；
- 每条 task 必须映射验收项 ID；
- 缺 Scenario 的 requirement 视为未定义验收标准。

## 7. 编码规范

1. **只做被要求的**：只实现点名范围及不实现就无法运行的部分。
2. **命名自解释**：禁止 `a` / `data` / `tmp` / `info` 等无意义命名；注释解释「为什么」。
3. **单一职责**：函数 ≤200 行、参数 ≤3、嵌套 ≤3、圈复杂度 ≤15；50 行是纯逻辑函数建议目标，不适用于组件/路由 handler。
4. **错误不吞**：禁止空 `catch`；错误必须记录、抛出或返回明确失败。
5. **DRY 有度**：相同逻辑第 3 次出现即提取；复制粘贴改常量视为缺陷。
6. **类型即文档**：禁止 `any` 漏网；外部输入用 Zod 校验；禁止 `@ts-ignore` / `@ts-expect-error` 掩盖错误，确需使用必须写原因并列入交付卡片。
7. **魔法数字禁止**：常量命名。
8. **禁止补丁累加**：不搞多层嵌套、超长函数、临时 flag 堆积。
9. **注释同步**：改代码后重新融合注释，删旧结论。
10. **性能**：
    - 禁止循环体内 `await` / IO；确需串行写 `// perf-ok: <理由>`；
    - `findMany` 必须有 `take` 或分页；确属小表全量写理由；
    - 列表接口必须分页；
    - 禁止 O(n²) 查找；
    - 渲染路径不做可缓存重复计算。
11. **安全卫生**：
    - 外部输入一律 Zod 校验；
    - SQL 参数化，禁止字符串拼接；
    - 不把用户内容交给 `innerHTML` / `dangerouslySetInnerHTML`，富文本先净化；
    - 用户输入进日志用结构化字段，不拼进消息；
    - 每个新增端点校验权限，不只靠前端隐藏；
    - 密钥/令牌不硬编码、不进前端 bundle、不进日志。
12. **卫生**：
    - 生产代码无 `console.log` / `debugger` / 临时开关 / 假数据 / 空实现；
    - 测试 mock 只在测试文件；
    - 不提交 `tmp-*` / `*.bak` / `*.orig` / 大段注释代码；
    - TODO 默认禁止；确需保留写 `TODO(YYYY-MM-DD, 责任人): 原因 + 移除条件`。

## 8. 质量门禁

`{{CHECK_CMD}}` 是唯一入口，建议包含（按阶段启用）：

| 阶段 | 门禁 | 拦什么 |
|---|---|---|
| 起步 | `lint` / `type-check` / `test` / `build` | 基本正确性 |
| 起步 | `check:imports` | 未声明依赖、幽灵依赖、编造包名 |
| 成长期 | `check:size` / `check:complexity` / `check:duplication` | 文件/函数膨胀、圈复杂度、克隆 |
| 成长期 | `check:docs` | 路由/handler/env 漂移 |
| 有 UI | `check:i18n` | 文案硬编码 |
| 有数据 | `check:perf` | 循环 `await`、无上界查询 |
| 有发布 | `check:publish` | 误发布 |
| 有分层 | `check:layout` / `check:dep-direction` | 目录与依赖方向 |

规则：

- **棘轮**：先登记存量，之后只许变小；`--update` 只收紧不放宽。
- **不得绕过**：无理由 `eslint-disable` / `@ts-ignore`、滥用 `// perf-ok`、把代码塞进排除目录、删测试、放宽断言。
- **门禁脚本/阈值/白名单改动按 L2**，需独立复核，并在 `docs/design/decisions.md` 登记；必须给改前/改后红绿对比；放宽需用户确认。
- **门禁能证明什么**：门禁全绿是最低门槛，不证明功能正确、交互可用、需求被满足。功能与边界靠验收清单，集成靠 E2E，视觉靠截图，需求靠独立复核。

## 9. 验收清单（五维）

每条结论只能是：**通过 / 不适用（附理由）/ 未验证（附原因）**。

### 9.1 功能
- 每个验收场景有对应测试且通过；
- 从真实入口跑通主流程；
- 测试名能映射回验收条目。

### 9.2 边界

| 边界 | 必须验证 |
|---|---|
| 空输入/空列表 | 提示、不崩溃 |
| 超长输入 | 有上限、明确报错 |
| 并发/重复提交 | 幂等、唯一约束、事务 |
| 权限/越权 | 每个端点校验；跨租户隔离 |
| 错误路径 | 400/401/403/404/409/500 与前端提示 |
| 断网/超时 | 重试/降级/提示，不白屏不吞错 |
| 刷新/深链 | 状态不丢、不串、不重复 |

### 9.3 集成
- 登录 → 进入 → 核心操作 → 预期结果；
- 刷新、重进路由、重新登录后状态正确；
- 前后端字段一致；
- E2E 脚本未覆盖的路径，用浏览器自动化或人工步骤补，附截图。

### 9.4 工程
- `build` 通过；`serve` 能独立跑构建产物；
- README 与实际一致；
- 依赖锁定，CI 可复现；
- 无硬编码密钥；`.env` 不入库，`.env.example` 只放占位。

### 9.5 卫生
- 无 TODO/FIXME/debugger/生产 `console.log`（扫本次改动）；
- 无占位实现/假数据/mock 残留；
- 文案走 i18n；
- 无重复代码；
- 无临时/备份文件；
- 无未使用符号/死代码。

### 9.6 高频失败形态（逐条排除）
- 语法合法、功能错误；
- 测试全绿但入口没接上、按钮无行为；
- 只在前端隐藏，后端没授权；
- 复制粘贴造第二套实现；
- `any` / `@ts-ignore` / 空 `catch` 压错误；
- 旧截图/旧输出冒充本次验证；
- 只测首次进入，刷新丢状态；
- 为过门禁拆分：指标转移而非降低。

## 10. 完成定义与交付卡片

**完成 = 验收清单全满足 + 五维通过 + 独立复核通过 + 证据可复现。**

六条硬条件：

1. `type-check` / `build` 本次 exit 0；
2. `test` 本次全绿，未改断言；
3. 主流程从用户入口跑通；UI 附 `artifacts/ui/<feature>.png`；
4. 无 TODO/FIXME/stub/占位/调试残留；
5. 新增前已搜索同职责实现；
6. 交付说明含「改了什么、为什么、怎么验证」。

交付卡片模板：

```markdown
### 交付卡片

**改了什么**
- ...

**为什么**
- 对应验收条目：...

**怎么验证的**
- `{{TYPE_CMD}}` → exit 0
- `{{TEST_CMD}}` → N passed
- `{{CHECK_CMD}}` → exit 0（贴尾部）
- E2E：脚本/步骤 + 结果 + 截图路径

**Diff 规模**：N 文件 / +X −Y（是否超预算：否 / 是，用户已于 ... 确认）

**门禁/基线改动**：无 / 列出

**逃生口**：`@ts-ignore` / `eslint-disable` / `perf-ok` / TODO：无 / 列出

**验收清单**
- [x] ...（证据：...）
- [ ] ...（未验证：原因 / 建议验法）

**五维结论**：功能 / 边界 / 集成 / 工程 / 卫生

**测试文件改动**：无 / 列出文件与理由

**最不确定的 3 处**
1. ...

**未验证的路径**
- ...
```

## 11. 独立复核协议

- **谁**：独立子代理 / 新会话 / 另一工具 / 用户本人。实现者自查不算。
- **输入**：任务契约 + 仓库 + diff（base..head）；**不给实现者自我评价**。
- **动作**：逐条运行或观察，不只读代码；每个「通过」给证据（命令输出、`文件:行号`、截图）；主动构造反例。
- **输出**：验收条目表 + 缺陷单（编号 + 严重级别 + 复现步骤）。
- **纪律**：复核者不改代码；改了就要换人。
- **闭环**：不通过 → 修复 → 重新复核。
- **L2 不得自我豁免**：没有独立复核能力时，状态只能标「未完成/待复核」。

复核提示词：

```text
你是独立评审，不是实现者。只依据 AGENTS.md、任务契约和仓库现状逐条验证。
不要相信实现者的结论；对每个「通过」给出可复现证据（命令输出 / 文件行号 / 截图）。
重点找反例：入口未接、刷新丢状态、权限只在前端、边界未处理、测试被放宽、复制粘贴。
输出：验收条目表（通过/不通过/未验证 + 证据）+ 缺陷单（按严重级别排序）。
```

## 12. 技能使用约定

> 未安装某个技能时，按 `docs/architecture/workflow.md` 的对应阶段步骤执行，产出物不变。

### 12.1 触发矩阵

| 时机 | 技能 / 动作 |
|---|---|
| 对话开始 | 先查可用技能，后行动 |
| 有想法 / 新功能 / 新项目 | 需求澄清与分类 |
| 规格已批、要拆任务 | 拆计划 |
| 要隔离工作区 | worktree / 分支隔离 |
| 单人执行计划 | 逐 task 执行 |
| 多 task 独立执行 | 每 task 双上下文 |
| 多任务互不依赖 | 并行分发 |
| 写功能 / 修 bug | 测试先行 |
| 出 bug / 测试失败 | 系统性调试 |
| 完成 task / 合并前 | 请求评审 |
| 收到评审意见 | 核实后采纳 |
| 声称完成前 | 验证优先 |
| 分支收尾 | 收尾决策 |
| 定视觉方向 | 视觉设计 |
| 做产品界面 | 界面设计 |
| UI 功能与视觉验收 | 浏览器自动化截图 |

### 12.2 冲突裁决

1. 技能默认落点与本文冲突 → 用本文路径（`changes/`、`docs/plans/`）。
2. 技能建议安装依赖 → 先问用户。
3. 技能要求「分 task 提交」与预算冲突 → 预算优先，先拆批次。
4. 技能要求「测试全绿即完成」 → 本文要求五维 + 独立复核，取更严。
5. 需求澄清阶段结束后只能接计划阶段；视觉设计放在设计阶段，不绕过规格/计划直接写代码。

---

## 13. 变更、提交与预算

- 一个 task 一个提交；功能改动与重构分开提交。
- 提交消息：`<类型>: <做了什么> — <为什么>`；类型用 `feat/fix/refactor/docs/test/chore`。
- 单次变更 ≤8 文件、净增 ≤400 行；超出先确认。
- 不 revert/format 与本任务无关的未提交改动。
- 开工前跑一次基线门禁，把既有红项写进契约；只对**新增**红项负责。
- 既有红项不得用改基线/删测试/放宽断言「洗绿」，也不得静默顺手修。

---

## 14. 安全红线

- 生产环境密钥必须为强随机值；开发默认值仅限本地。
- 密钥/令牌不得进前端 bundle、不得进日志、不得硬编码。
- 每个端点校验权限；前端隐藏不是授权。
- 外部输入 Zod 校验；SQL 参数化；输出编码/净化。
- 高风险操作（执行代码、删除数据、对外发送）必须审批或二次确认。
- 日志结构化；用户输入不拼进消息行。
- 新增依赖先问，并检查已知漏洞与维护状态。
