# 新项目开发流程手册（Greenfield Workflow）

> 适用：从零开始的新项目、新子系统、需要重建的旧模块。
> 定位：回答「按什么顺序做、用什么方法、产出什么、怎么证明做完了」。
> 配套：项目根 `AGENTS.md`（规则，优先级更高）。规则冲突时以 `AGENTS.md` 为准，本手册只描述执行路径。
> 可选工具：`brainstorming`、`writing-plans`、`test-driven-development`、`systematic-debugging`、`requesting-code-review`、`verification-before-completion`、`frontend-design`、`interface-design`、`webapp-testing` 等技能；未安装时按本文档的步骤直接执行。

---

## 0. 一页速览

```text
想法
 ├─ 阶段 0  立项准备        → 仓库/文档骨架/基线
 ├─ 阶段 1  契约与验收      → 任务契约 + 验收清单        ★闸门 1
 ├─ 阶段 2  设计            → design.md + 设计系统       ★闸门 2
 ├─ 阶段 3  计划            → 任务计划（TDD 步骤级）
 ├─ 阶段 4  骨架 + 分片实现  → 每个 task 红→绿→回归→提交
 ├─ 阶段 5  自动闸门        → check + build + E2E + 截图
 └─ 阶段 6  独立复核        → 缺陷单 → 修复 → 再复核     ★闸门 3
                              → 交付卡片 + 合并
```

三条铁律：

1. **没有验收标准，不进入实现。**
2. **没有先失败的测试，不写生产代码。**
3. **没有独立复核，不宣布完成。**

---

## 1. 三套体系的分工与优先级

| 体系 | 负责 | 不负责 |
|---|---|---|
| `AGENTS.md` | 红线、分级、门禁、完成定义、证据要求 | 具体某天先做哪一步 |
| 方法技能集 | 从想法到计划、执行、复核的方法与节奏 | 项目红线、业务取舍 |
| UI 三件套 | 视觉方向、设计系统、界面验收 | 后端、数据、权限 |

**优先级**：用户直接指令 > `AGENTS.md` > 技能默认值。技能里的「默认落点/默认流程」与本项目规则冲突时，改技能行为，不改项目规则。

### 1.1 常见冲突裁决

| 冲突 | 技能默认 | 本项目做法 |
|---|---|---|
| 规格/计划落点 | `docs/superpowers/specs|plans/` | `changes/<kebab-name>/` + `docs/plans/YYYY-MM-DD-NNN-feat-*.md` |
| 新增依赖 | 技能建议即装 | 先问用户，说明现有依赖为何不够 |
| 单次改动规模 | 按 task 提交，无上限 | ≤8 文件、净增 ≤400 行；超出先确认并拆分 |
| 测试 | TDD | 不得改断言、加特判、放宽类型；改测试必须单独说明 |
| 复核 | code review subagent | 独立上下文 + 逐条证据 + 缺陷单；L2 强制 |
| 文档 | 可后补 | 代码与文档同轮完成，未同步 = 未完成 |
| UI 顺序 | 各自适用 | 定方向 → 定系统 → 写代码 → 截图验收 → 反面清单自检 |

### 1.2 需要用户拍板的 7 个决策点

1. 是否创建隔离 worktree；
2. 执行方式：单人执行还是「每 task 双上下文」；
3. 是否新增依赖 / 工具；
4. 改动是否超出 8 文件 / 400 行预算；
5. 是否调整门禁阈值或基线（高风险，按 L2 处理）；
6. UI 视觉方向（2–3 个方案里选）；
7. 合并策略：直接合并 / PR / 保留分支。

## 3. 规模分级

| 级别 | 判定 | 最低流程 | 复核 |
|---|---|---|---|
| L0 | 纯文档/注释/文案，无行为变化 | 相关门禁 + 说明改了什么 | 可免 |
| L1 | 单模块行为变更、修 bug | 契约 + 测试 + `check` | 用户抽查 |
| L2 | 新项目、新功能、跨模块、架构/数据/安全 | 契约 + 规格 + 骨架 + 分片 + E2E + 全量门禁 | **独立复核强制** |

**新项目默认 L2。** 不从 L2 降级；发现隐藏复杂度时只升级不降级。

## 4. 阶段 0：立项准备

**目标**：让项目「能跑、能检查、能记录」，不写业务代码。

动作清单：

- [ ] 初始化仓库、`.gitignore`、`.env.example`（只放占位值）
- [ ] 包管理器与 workspace 结构确定（`apps/` / `libs/` / `tools/`）
- [ ] 所有包 `private: true`；确需发布 npm 单独决策
- [ ] 建立文档骨架：`readme.md`、`prd.md`、`project_plan.md`、`docs/design/README.md`、`docs/architecture/layout.md`、`docs/plans/`、`changes/`、`artifacts/ui/`
- [ ] 建立最小门禁：`lint`、`type-check`、`test`、`build`、依赖检查；聚合成一条 `check`
- [ ] 跑一次全量门禁，把既有红项登记进首个任务契约（空仓记为「无」）
- [ ] 建立 CI，只调用同一条 `check`（禁止本地与 CI 两套口径）

**退出标准**：`install → check → build → serve` 四步从干净环境可复现。

## 5. 阶段 1：契约与验收

**方法**：先分类（spike / bounded / architectural）。

新项目没有既有流程可改，**只能是 architectural**，不能自称 bounded 省掉规格。

### 5.1 必须先问清的 5 个问题

1. 使用者是谁？在什么场景下打开它？
2. 他来这里要完成的那**一个动词**是什么？
3. 什么算成功？能量化吗？
4. 明确**不做**什么？
5. 有哪些硬约束（技术栈、合规、预算、期限、必须复用的系统）？

一次问一个，不要一口气抛 5 个。

### 5.2 任务契约（L1/L2 必填）

```markdown
### 任务契约
- 目标：一句话，可验收。
- 入口 / 平台：用户从哪个页面、命令或接口进入。
- 技术栈 / 复用约束：用哪些现有包与模式；明确不引入的新依赖。
- 必须支持的交互：点击 / 输入 / 键盘 / 语音 / 刷新 / 返回。
- 必须覆盖的场景：正常、边界、失败、权限、并发。
- 明确不做：本次不碰的范围。
- 完成标准：3~8 条，每条对应一条可执行命令或可观察行为。
- 计划：编号步骤 → 每步的验证方式。
- 规格工件（L2）：proposal → specs/design → tasks（tasks 最后写）。
```

### 5.3 验收清单（四类，逐条编号）

```markdown
| ID | 类型 | 验收项 | 验证方式 | 证据 | 结论 |
|---|---|---|---|---|---|
| AC-1 | 功能 | 登录后进入首页 | E2E 脚本步骤 1-3 | 截图 + 日志 | 待验 |
| AC-2 | 边界 | 空列表显示空态 | 用例 + 截图 | test 名 + png | 待验 |
| AC-3 | 集成 | 刷新后状态不丢 | 手工/脚本 | 录屏或 png | 待验 |
| AC-4 | 卫生 | 无 TODO/console.log | 扫描命令 | diff 输出 | 待验 |
```

**每类至少一条**：功能、边界、集成、卫生。写不出可执行验证方式的条目，删掉或改写，不要保留。

### 5.4 规格写法

```markdown
### Requirement: 用户登录
The system SHALL 允许已注册用户使用邮箱与密码登录。

#### Scenario: 正确凭证
- **WHEN** 用户提交有效邮箱与密码
- **THEN** 返回会话令牌并跳转首页

#### Scenario: 密码错误
- **WHEN** 用户提交错误密码
- **THEN** 返回 401 且不泄露账号是否存在
```

**闸门 1**：把「我理解的目标 + 验收项」复述给用户，明确说「确认后我才开始设计/实现」。

## 6. 阶段 2：设计

### 6.1 技术设计清单

- 数据模型：表 / 字段 / 索引 / 迁移 / 回滚
- 接口：路径、入参、出参、错误码、分页、幂等键
- 权限：每个端点校验什么角色/作用域；前端隐藏不算授权
- 并发：唯一约束、事务边界、重复提交
- 失败：超时、重试、降级、部分失败
- 可观测：结构化日志字段、关键指标
- 安全：输入校验、参数化查询、输出编码、密钥管理

### 6.2 UI 设计（有界面时）

顺序固定：

1. **定视觉方向**——调性、字体、色彩、布局概念。要求给出 4–6 个命名色值、字体角色、一版 ASCII 线框；明确避开模板化默认款。
2. **落成设计系统**——语义化 token（`--ink` 而不是 `--gray-700`）、层级、间距、圆角、状态（空/加载/错误/禁用/成功）、响应式断点、动效原则。写入 `.interface-design/system.md`。
3. 设计系统经用户确认后，才允许写界面代码。

> 判断标准：换一个 AI 用同样的 brief 会不会产出几乎一样的界面？会，就还没设计完。

**闸门 2**：用户 review `design.md` + 设计系统；口头「可以」只允许继续写规格，不允许直接开工。

## 7. 阶段 3：计划

要求：

- 读者是「没看过这个仓库的工程师」：每个 task 写清**改哪个文件、函数签名、用哪个测试证明**。
- 每个 step 只做一件事、有可检验结果：
  - 写失败测试 → 跑到失败 → 最小实现 → 跑到通过 → 全量回归 → 提交。
- **Task 1 固定是 walking skeleton**：目录、数据模型、主入口跑通，能 build、能启动、能冒烟。
- 每个 task 独立可测、可回滚；一个 task 一个提交。
- 列出超出 8 文件 / 400 行预算的批次，提前拆。
- `tasks.md` **最后写**，每条 task 映射验收项 ID。

计划模板：

```markdown
### Task 2: 实现登录接口
- 文件：`apps/api/src/auth/login.ts`（新建）、`apps/api/src/auth/index.ts`（修改）
- 接口：`POST /api/auth/login`，入参 `{email, password}`，成功 200 `{token}`，失败 401 `{code}`
- 步骤：
  - [ ] 写失败测试：正确凭证返回 token
  - [ ] 运行测试，确认因「未实现」失败
  - [ ] 最小实现：查用户 + 校验密码 + 签发 token
  - [ ] 运行测试通过 + 全量回归
  - [ ] 提交
- 验收映射：AC-1、AC-5
```

## 8. 阶段 4：骨架与分片实现

### 8.1 隔离

先检测是否已在隔离工作区；未隔离且用户未声明偏好时，**先问是否创建** worktree。一人一分支，分支名与任务同名。

### 8.2 选择执行方式

| 方式 | 适用 | 成本 | 质量保障 |
|---|---|---|---|
| 单人执行 | task 较少、上下文连贯、你亲自实现 | 低 | 每 task 自测 + 最后统一一次独立复核 |
| 每 task 双上下文 | task 多且独立、需要每 task 新鲜视角 | 高 | 每 task 独立实现者 + 独立复核 |

选择后不来回切换。执行期间不逐 task 问「要不要继续」，遇以下四种情况才停：不可逆/破坏性操作、安全敏感操作、工作区外的副作用（合并/推送/发布）、计划坏到每条路都是猜。

### 8.3 每个 task 的固定循环（TDD）

1. **RED**：写一个会失败的测试，只测一个行为。
2. **验证红**：运行，确认失败原因正确（不是语法错误、不是环境问题）。
3. **GREEN**：写最小实现让它通过，不做多余设计。
4. **验证绿**：运行该测试 + 全量回归。
5. **REFACTOR**：在绿的前提下清理，行为不变。
6. **提交**：一个 task 一个提交，消息写「做了什么 + 为什么」。

铁律：**先写了实现代码？删掉，从测试重来。** 不保留作「参考」。

### 8.4 决策留痕

执行中遇到规格/计划没覆盖的取舍，不要停下来问，做决定并记录：

```text
Ruling: <决定> — <理由> — <错了的代价>
```

秘密偏离计划（不记录）视为缺陷。

### 8.5 调试

出现 bug / 测试失败，先系统性调试：

1. 复现（最小输入、稳定步骤）；
2. 读错误全文与相关代码；
3. 提出假设并设计能证伪的实验；
4. 一次只改一个变量；
5. 修复后补一个能锁住该 bug 的回归测试。

禁止「先改一行看看」。

### 8.6 并行

2 个以上**互不共享文件**的独立任务，才可以并行。共享同一文件、同一迁移、同一接口契约的任务必须串行。

## 9. 阶段 5：自动闸门与验证

### 9.1 顺序（不可颠倒）

| 步骤 | 命令 | 通过标准 |
|---|---|---|
| 1 类型与单测 | `npm run type-check`、`npm test` | exit 0，0 failed |
| 2 全量门禁 | `npm run check` | exit 0 |
| 3 构建 | `npm run build` | exit 0，产物存在 |
| 4 产物运行 | `npm run serve` | 停掉 dev server 后入口可访问 |
| 5 E2E | `node scripts/integration-test.mjs` 等 | 主流程通 |
| 6 UI 验收 | Playwright 截图 | 截图存在且符合设计 |
| 7 卫生扫描 | 见 9.4 | 输出为空或有理由 |

### 9.2 五维验收（逐条给结论）

| 维度 | 必须回答 |
|---|---|
| 功能 | 每个验收场景有对应测试且通过；从真实入口跑通 |
| 边界 | 空输入、超长、并发、权限、错误码、断网、刷新/深链 |
| 集成 | 前后端字段一致；刷新/重进状态正确；E2E 证据 |
| 工程 | build/serve 可跑；README 与实际一致；依赖锁定；无密钥 |
| 卫生 | 无 TODO/调试输出/占位/临时文件/死代码；i18n 无新增硬编码 |

每条只能是：**通过 / 不适用（附理由）/ 未验证（附原因和建议验法）**。不允许空白。

### 9.3 UI 截图

要求：

- 用本机**已安装 Playwright** 的解释器；不要为旧 Python 另装 Playwright，不要跑 `playwright install`（离线环境会挂）。
- `sync_playwright()` + headless chromium；
- 动态页面先 `wait_for_load_state('networkidle')`；
- 覆盖：默认态、空态、错误态、加载态、移动断点；
- 结束 `browser.close()`；
- 存 `artifacts/ui/<feature>.png`，交付说明必须引用。

若使用 `webapp-testing` 类的辅助脚本，路径随安装位置不同，按本机实际路径调用。示例（DSH 安装形态）：

```bash
# 启动服务 + 跑截图脚本，端口随项目替换
python3 <skills-dir>/webapp-testing/scripts/with_server.py \
  --server "npm run dev" --port 5173 -- python3 shot.py
```

### 9.4 卫生扫描

```bash
# 已跟踪文件的新增行
git diff HEAD -U0 -- '*.ts' '*.tsx' '*.mjs' | \
  awk '/^\+\+\+ b\//{f=$2} /^\+/ && !/^\+\+\+/ && /TODO|FIXME|HACK|XXX|debugger|console\.(log|debug)/ {print f": "$0}'

# 未跟踪的新文件
git ls-files --others --exclude-standard -- '*.ts' '*.tsx' '*.mjs' | \
  while IFS= read -r f; do grep -HnE 'TODO|FIXME|HACK|XXX|debugger|console\.(log|debug)' "$f"; done
```

输出应为空，或有明确理由并写进交付卡片。

### 9.5 识别「假绿」

- 测试全绿，但入口没接上、按钮无行为；
- 只测了首次进入，没测刷新/重进；
- 只在前端隐藏，后端没授权；
- 用 `any` / `@ts-ignore` / 空 `catch` 压错误；
- 改了断言或基线让门禁变绿；
- 用旧截图/旧输出冒充本次验证。

## 10. 阶段 6：独立复核与收尾

### 10.1 复核输入

只给三样：**任务契约 + 仓库 + diff（base SHA → head SHA）**。**不要给实现者的自我评价**，避免锚定。

### 10.2 复核提示词

```text
你是独立评审，不是实现者。只依据 AGENTS.md、任务契约和仓库现状逐条验证。
不要相信实现者的结论；对每个「通过」给出可复现证据（命令输出 / 文件:行号 / 截图）。
重点找反例：入口未接、刷新丢状态、权限只在前端、边界未处理、测试被放宽、复制粘贴。
输出：验收条目表（通过/不通过/未验证 + 证据）+ 缺陷单（按严重级别排序）。
不要修改代码；发现问题只报告。
```

### 10.3 缺陷单

```markdown
### 缺陷 3（Critical）
- 位置：`apps/api/src/auth/login.ts:42`
- 复现：错误密码登录 → 返回 200
- 期望：401；实际：200
- 证据：curl 输出 / 测试日志
- 建议：先查用户再统一返回 401，避免账号枚举
```

### 10.4 闭环

不通过 → 修复 → **重新复核**（换人/换上下文）→ 通过。复核者改了代码，就变成实现者，必须换人复核。

### 10.5 交付卡片

```markdown
### 交付卡片

**改了什么**
- ...

**为什么**
- 对应验收条目：AC-1 / AC-3 ...

**怎么验证的**
- `npm run type-check` → exit 0
- `npm test` → N passed
- `npm run check` → exit 0（贴尾部）
- E2E：脚本 + 结果 + 截图路径
- 截图：`artifacts/ui/<feature>.png`

**Diff 规模**：N 文件 / +X −Y（是否超预算：否 / 是，用户已于 ... 确认）

**门禁/基线改动**：无 / 列出（高风险，独立复核重点）

**逃生口**：`@ts-ignore` / `eslint-disable` / TODO：无 / 列出

**验收清单**
- [x] AC-1（证据：...）
- [ ] AC-2（未验证：原因 / 建议验法）

**五维结论**：功能 / 边界 / 集成 / 工程 / 卫生

**最不确定的 3 处**
1. ...

**未验证的路径**
- ...
```

### 10.6 收尾

测试全绿 → 给出合并 / PR / 保留分支选项 → 执行 → 清理 worktree。同步文档，再宣布完成。

## 11. 技能触发矩阵

| 时机 | 技能 / 动作 | 产出 |

| 写功能 / 修 bug | 测试先行 | 红→绿→重构 |

| 完成 task / 合并前 | 请求评审 | 独立评审 |

## 12. 节奏建议

| 项目规模 | 建议节奏 |
|---|---|
| 1 周 MVP | 阶段 0–3 压缩到 1 天；1 个骨架 + 3–5 个功能切片 |
| 1 个月 | 每周一个可演示切片；每切片完整走阶段 4–6 |
| 3 个月以上 | 阶段 1–3 每两周回归一次；架构决策进 `decisions.md` |

**成本控制**：计划越具体，执行越便宜；「每 task 双上下文」只在 task 真正独立时用；小改动走 L1，不要为了「流程完整」给一行文案改动配规格。
